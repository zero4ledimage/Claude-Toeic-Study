> 開發方式:Claude Code 開發,GitHub Pages 部署
> 文件狀態:v1.0定案,待轉交Claude Code開發

## 1. 專案背景與目標

### 1.1 使用者現況
- 年齡45歲,每日可學習時間約2-3小時
- 英文讀、聽程度約為多益550分水準
- 英文說、寫程度約為多益400分水準(對應雅思口說寫作約5.0-5.5分程度)
- 需同時考慮記憶力隨年齡下降的因素,學習設計需仰賴間隔重複而非硬背

**實際學習時間結構**:

| 時段 | 時長 | 型態 | 適合活動 |
|---|---|---|---|
| 週一至週五(白天) | 合計1.5小時 | **零碎、多次** | FSRS到期單字複習(3.1/3.7節)、單則短聽力、單篇短閱讀 |
| 週一至週五(晚上) | 0.5-1小時 | 完整一段 | 口說寫作維持劑量練習(1.3節)、閱讀/聽力拆解器深度使用 |
| 週六、週日 | 各2-3小時 | 完整 | 官方真題模擬考、寫作批改沙盒完整練習、口說完整練習、每週弱點回顧 |

使用者習慣把白天與晚上的學習分開進行,而非一次做完。此結構直接影響3.8節的情境化學習排程設計。

### 1.2 雙考試目標與時程

| 考試 | 目標分數 | 測驗內容 |
|---|---|---|
| TOEIC (多益 Listening & Reading) | 750 / 990 | **僅聽力+閱讀**,不含口說寫作 |
| IELTS (雅思) | 7.5 / 9.0 (Overall) | 聽、說、讀、寫四項獨立計分後取平均 |

**確定的時程(序列式,非平行)**:

| 階段 | 時間 |
|---|---|
| Phase 1(多益衝刺) | 2026年7月-12月 |
| 多益應考+放榜 | 2026年12月 |
| 決策點(確認是否達標,才報考雅思) | 2026年12月底-2027年1月初 |
| Phase 2(雅思衝刺,9個月) | 2027年1月-9月 |
| 雅思應考 | 約2027年9-10月 |

整體專案時程約**14-15個月**(2026年7月-2027年9-10月),而非最初設想的約9個月——因為雅思的讀書準備(不只報名)也要等多益放榜確認達標後才開始,兩考試完全序列進行,不平行。

- ✅ **多益應考時程已確認:2026年12月**
- ✅ **雅思讀書準備延後至多益達標後才開始**(2027年1月起),已反映於上表

### 1.3 兩階段學習策略

由於TOEIC L&R完全不考口說寫作,而使用者現有讀聽底子(550分)優於說寫(400分),學習順序採**技能對齊考試結構**的分期,而非原先"閱讀寫作 vs 聽力口說"的分組方式:

**第一階段(2026年7-12月,對應多益衝刺)**
- 主力:閱讀 + 聽力
- 開發優先序:句子/文法拆解器、FSRS詞彙與長句複習引擎、聽力模組(含TTS或真實音檔)
- 口說寫作:**先做輕量版雛形**(基本版寫作批改沙盒、基本版口說錄音轉文字,不含精緻化評分邏輯),**搭配每日15-20分鐘寫日記或跟讀模仿的習慣維持**,避免完全歸零到Phase 2才重新建立手感

**第二階段(2027年1-9月,對應雅思衝刺,多益確認達標後才開始)**
- 主力:口說 + 寫作(從400分程度需大幅躍升至7.5分對應水準,躍升幅度大,9個月完整準備期)
- 開發優先序:**強化**Phase 1已有的寫作批改沙盒(補上Task 1圖表描述 / Task 2議論文分流)、**強化**口說模組(補上更完整的AI評語邏輯)
- 同時銜接雅思版的閱讀聽力(題型與多益不同,需要額外適應期,非從零開始)

## 2. 內容策略:官方題庫 + AI生成雙軌並行

### 2.1 為什麼需要雙軌

| 層級 | 內容來源 | 用途 | 限制 |
|---|---|---|---|
| 錨點層(Ground Truth) | 官方/高信度真題 | 每2-4週模擬考,校準真實分數與弱點 | 取得成本高、數量有限、有版權 |
| 練習層(AI生成) | Claude API即時生成 | 每日高頻率練習、弱點加強、批改 | 難度未經統計校準,不能完全取代真題判斷分數 |

Claude不能複製或重製ETS、劍橋雅思的原題(版權限制),只能生成風格相似的原創題目。因此策略是:**用官方真題模擬考找出具體弱點 → 把弱點餵給Claude大量生成同類型原創練習題**,兼顧真實校準與練習量,且完全合法。

### 2.2 建議的官方題庫來源

**多益(TOEIC):**
- 忠欣股份有限公司為ETS在台灣的官方代理,市面標示「新制多益官方全真模擬試題」系列(ETS授權或忠欣相關字樣)最貼近真實考試
- 第三方口碑品牌:Hackers Academia(韓國多益書籍龍頭)、Barron's、我識出版集團「挑戰新多益」系列,可於博客來、誠品、momo購物網購得
- ETS官網(ets.org)有少量免費官方範例題

**雅思(IELTS):**
- **劍橋雅思(Cambridge IELTS)真題系列**:劍橋大學出版社出版,由出題團隊直接編寫,是公認最權威的官方練習題本,目前已出版至第21冊(2026年6月)。建議從第15冊左右開始,題型難度較貼近現行考試
- 需先確認報考Academic或General Training版本,兩者題本不同
- 台灣可透過華泰網路書店等通路購買正版,或劍橋大學出版社官網訂購
- British Council / IDP(官方雅思考試機構)官網提供付費官方模擬測驗服務,評分邏輯與真實考試一致

**採購時程建議**:
- **多益**:現在(2026年7-8月)即可購入,距12月應考約5個月,標準配送即可,搭配2-4週一次的模擬考排程開始使用
- **雅思**:建議2026年11-12月左右(多益應考前後、確認是否進入Phase 2時)再購入,避免現在買太早,屆時劍橋雅思可能又有更新版本;書中通常同時包含Academic與General Training的補充題目,現在不用急著決定應考類別

**注意**:網路上搜尋劍橋雅思真題常會出現非官方授權的免費PDF下載連結,這類來源版權未經授權,且掃描品質不穩定,建議一律採購正版,尤其這些內容要作為系統的分數校準錨點,來源不準確會直接誤導你對真實程度的判斷。

## 3. 核心功能規格

### 3.1 FSRS間隔重複引擎
- 依據使用者實際作答結果動態調整複習排程(而非固定天數),更符合45歲記憶力現況的設計目標
- 適用對象:單字、核心句型、易錯文法點

### 3.2 閱讀/聽力素材拆解器
- 匯入一段閱讀或聽力文字後,AI自動拆解「核心單字」「語法結構」「常考考點」
- 拆解結果自動進入FSRS複習佇列

### 3.3 寫作批改沙盒
- 輸入一段寫作(雅思Task 1圖表描述 / Task 2議論文 / 多益商務書信情境擇一模式),AI輸出:
  1. 修正版(文法用詞錯誤+說明原因)
  2. 升級版(改寫為目標分數對應水準的進階句型與詞彙)
- Task 1與Task 2需分開設計提示詞(prompt),因評分重點不同(前者重資料描述準確度,後者重論證邏輯)

### 3.4 口說練習模組(**Phase 1先做輕量版,Phase 2強化**)
- **Phase 1輕量版**:使用Web Speech API做語音轉文字,由Claude給基本的內容組織建議,先求有可用的練習迴圈
- **Phase 2強化版**:補上更完整的AI評語邏輯(流暢度、詞彙多樣性等維度)
- **已知限制**:此方案無法評估發音準確度與語速/停頓等音訊層面的流利度,這部分是雅思口說四大評分項目之一,單靠STT+LLM評不到,如需要應另外評估音訊分析方案(暫不在本次開發範圍)

### 3.5 錯題本 / Error Log
- 自動記錄每次作答錯誤,標註錯誤類型(單字/文法點/邏輯理解),作為AI生成延伸練習題的依據

### 3.6 模擬考排程與進度追蹤儀表板

**功能一:分數趨勢圖表**
- 按技能(多益:聽力/閱讀;雅思:聽/說/讀/寫)繪製每次模擬考分數的時間序列折線圖

**功能二:目標達成路徑對照**
- 依12月多益、預計雅思應考日反推「當前應落在的分數區間」參考線,與實際模擬考分數疊圖比對,呈現超前/落後進度,而非僅憑感覺判斷

**功能三:弱點分布圖**
- 將錯題本(3.5節)的錯誤類型(單字/文法點/邏輯理解)統計為雷達圖或長條圖,呈現持續性弱點與已改善項目

**功能四:週期性文字摘要(AI自動生成)**
- 每週或每次模擬考後,以Haiku 4.5(低成本)根據當週讀書時數、錯題趨勢、複習完成狀況,生成一段白話文字摘要與具體建議,例如指出哪類題型錯誤率下降、哪類仍需加強
- 比起純數字圖表,文字化解讀更利於快速回顧

**功能五:讀書時數與一致性追蹤**
- 記錄每日實際讀書時數 vs. 規劃時數、連續學習天數
- 依1.1節的時間結構,分別追蹤「週間零碎時段完成率」與「週末完整時段完成率」,呼應年齡與記憶力現況需要的一致性設計

以上功能建立在既有的`progress_records`、`error_log`、`study_sessions`資料表上(見4.5節),定期(2-4週)提醒進行官方真題模擬考。

### 3.7 單字互動查詢與重點單字清單

**適用範圍**:閱讀測驗解答畫面、聽力測驗逐字稿/解答畫面

**功能一:滑鼠停留顯示翻譯與音標**
- 閱讀/聽力文字需以「每個單字獨立HTML元素(如 `<span data-word="...">`)」呈現,而非整段純文字,以便偵測滑鼠停留在哪個單字上
- 滑鼠停留約0.3秒後(避免滑過即跳出,干擾閱讀),彈出提示框顯示:音標 + 中文釋義
- 查詢資料來源:本地載入的ECDICT字典資料(見2.3節),**不呼叫Claude API**,確保即時反應且無額外成本
- **手機/觸控裝置替代方案**:觸控螢幕沒有hover狀態,需改為「點一下單字」跳出提示框、點其他區域關閉

**功能二:加入重點單字清單**
- 提示框內加入「＋加入單字清單」按鈕
- 按下後,系統擷取:該單字 + 完整情境句(從當下閱讀文章或聽力逐字稿截取上下文),寫入vocab_items資料表
- 新加入的單字次日起自動進入3.1節FSRS複習佇列,不需另建複習邏輯
- 可選:加入時額外呼叫一次Claude API,生成該單字在此句情境下的精確用法說明(因為是低頻率的重點動作,不是每次hover都呼叫,成本可控)

**功能三:每日快速複習**
- 即FSRS到期複習清單的呈現介面:單字卡正面顯示「情境句(單字挖空)」,背面顯示「音標+翻譯+原句」,提供記得/不記得的複習回饋

**待確認/待驗證事項**:
- ✅ 音標系統已確認採用**KK音標**(台灣英語教學慣例)
- ⚠️ **KK音標轉換需求**:KK音標是台灣特有系統,ECDICT為中國大陸開發專案,音標欄位很可能是IPA或DJ格式而非KK。建議下載ECDICT資料後,建立IPA/DJ→KK的符號對照轉換表(約20-30組符號替換規則,例如KK不使用長音符號「:」、以/ɛ/取代/e/等),對音標欄位做一次性批次轉換並存下結果,不需每次查詢即時轉換,也不需要AI協助,屬於規則明確的工程工作
- [ ] ECDICT完整340萬詞條資料量偏大,建議篩選出多益/雅思常用範圍詞彙子集(約15,000-20,000字),或改用IndexedDB本地索引,避免一次性載入全部資料拖慢網頁

### 3.8 情境化學習排程建議

依1.1節的實際時間結構,系統依使用者當下所處時段,主動推薦適合的活動類型,而非讓使用者每次都要自己想「現在該做什麼」:

| 情境 | 系統建議活動 |
|---|---|
| 週間白天零碎時段(5-20分鐘) | FSRS到期單字複習(3.1/3.7節)、單一短聽力片段 |
| 週間晚上完整時段(0.5-1小時) | 口說寫作維持劑量練習、閱讀/聽力拆解器深度使用 |
| 週末完整時段(2-3小時) | 官方真題模擬考(2-4週排程一次)、寫作批改沙盒完整練習、口說完整練習、每週弱點回顧(3.6節功能四) |

- 使用者開啟工具時,系統可依當下星期幾/時間自動判斷情境並給出建議,也允許手動切換(例如週間白天臨時有完整時段時)
- 此設計呼應45歲記憶力現況的核心原則:零碎時間做高頻率複習、完整時間做需要專注力的深度練習,而非兩者混用

### 3.9 API預算控管與每日開銷視覺化

**追蹤機制**
- 於4.1.1的Cloudflare Workers中介層加入用量記錄,使用Workers KV儲存每日/每月累計花費估算(依實際token數 × 4.4節模型定價換算)
- 每月1日自動歸零重新累計

**三層預算門檻**
| 門檻 | 行為 |
|---|---|
| USD 10 | 前端顯示提示訊息(不阻擋使用),讓使用者掌握花費節奏 |
| USD 20 | 前端顯示加強版警示訊息(不阻擋使用) |
| USD 30 | **硬性上限**,Worker直接拒絕當月剩餘的AI相關請求,前端顯示「本月AI預算已達上限,將於X月X日重置」,並提供手動解除選項應急,避免真的有急用時被完全卡住 |

**每日開銷視覺化**

### 4.1 整體架構
- **前端**:GitHub Pages(純靜態網站,無後端伺服器),任何裝置透過瀏覽器開啟網址即可使用,不需要登入GitHub帳號
- **資料儲存**:Google Drive API(使用者已有Google AI Pro訂閱含2TB儲存空間,但實際學習資料檔案很小,儲存空間非瓶頸)
- **AI服務**:Anthropic API(Claude),透過中介層呼叫(見4.1.1,**不可直接在前端呼叫**)

### 4.1.1 ⚠️ 重要修正:API金鑰安全性與Cloudflare Workers中介層

**問題**:GitHub Pages發布的網站是純前端程式碼,任何人只要在瀏覽器「檢視網頁原始碼」就能看到全部JavaScript內容。如果Anthropic API金鑰直接寫在前端程式碼裡,**不論GitHub repo設為public或private都無法避免金鑰外洩**——因為repo的公開/私有設定只影響原始碼倉庫本身能不能被瀏覽,不影響「已發布網站」的前端程式碼是否可被檢視。網路上有機器人專門掃描公開網站尋找外洩的API金鑰並濫用,可能導致帳單短時間暴增。

**解法**:加入一層輕量中介伺服器,金鑰只存放在這一層,前端完全看不到:
- 建議使用 **Cloudflare Workers**(免費額度每日10萬次請求,個人使用足夠)
- 前端呼叫自己的Cloudflare Worker端點 → Worker用環境變數保存的API金鑰呼叫Anthropic API → 回傳結果給前端
- 金鑰全程只存在於Worker的伺服器端環境變數,不會出現在任何前端程式碼或瀏覽器可見內容中

### 4.1.2 GitHub repo public/private說明(更正)
- **重要更正**:免費GitHub帳號下,GitHub Pages**僅支援public(公開)repo**,private repo無法啟用GitHub Pages,除非升級GitHub Pro等付費方案
- 由於4.1.1已將API金鑰移至Cloudflare Workers,repo本身設為public或private已不影響金鑰安全,因此**建議repo可設為public**(免費、無限制),除非有其他理由(例如不想公開prompt設計或程式碼)才需考慮付費升級Pro改為private

### 4.2 Google Drive串接設計
1. Google Cloud Console建立專案,啟用Google Drive API
2. OAuth同意畫面設定為External類型,加入使用者Gmail為測試使用者,授權範圍使用 `drive.file`(僅能存取本應用建立的檔案,較安全)
3. 建立OAuth 2.0用戶端ID(類型:網頁應用程式),將GitHub Pages網址填入「已授權的JavaScript來源」
4. 前端採用Google Identity Services的token client模式(而非傳統offline refresh token模式),原因:配置為External+測試中狀態的OAuth應用,refresh token會在7天後過期,除非通過Google正式驗證流程——對個人工具而言不需要為此走驗證流程。token client模式每次開啟網站做一次輕量Google登入即可取得約1小時效期的存取權杖,完全繞開此限制,且本來就是為純前端無後端架構設計的標準模式
5. 使用取得的存取權杖呼叫Drive API,讀寫JSON格式的進度/單字/錯題資料檔案

### 4.3 跨裝置使用方式
- 任何裝置(手機、公司電腦、家用電腦)只要用系統瀏覽器(不建議用LINE/FB等App內建瀏覽器)開啟GitHub Pages網址,並以同一Google帳號登入授權,即可存取同步的學習資料
- 網址本身公開可訪問,但學習資料的實際存取仍受Google帳號登入把關
